Open firmware tools

Digitone II Mods

Tools that change what your Digitone II can do. We built them by reading the firmware, measuring it, and writing down what turned out to be wrong. Everything here rebuilds and re-verifies an image before it will hand it to you.

Read this before you flash anything. These tools make firmware images. They do not send anything to an instrument, and they never will. You put an image on your device yourself, as a separate step that you decide to do.

Make sure that you can go back to stock first. The Early Start-up Menu can flash the stock firmware over MIDI. Do this one time with the stock file, before you flash a modified file. If that route does not work on your device, nothing here is safe to use. Also back up your +Drive first.

Getting a transient out of an ordinary sample

A slot is 100 ms of percussive attack, and most samples are neither. Two different problems, worth keeping apart:

  • Fitting: mono, 48 kHz, 100 ms, starting at the attack rather than at whatever silence the file begins with. That is what --prepare does.
  • Separating: pulling the percussive layer out of a sample that is also pitched. That is real signal processing. transientsplit (MIT, by Mikko Vihonen) already does it. It splits a sample into transient, tonal and residual parts in your browser, and it uploads nothing.

So, for any sample:

  1. Run the sample through transientsplit.
  2. Keep the transient stem.
  3. Give that stem to --prepare.

We link to transientsplit and do not bundle it. It is the tool of a different author, it works, and a copy from us would only be worse.

Tuning it per sample

--prepare finds the attack and keeps a few milliseconds before it. One number cannot be right for every sound. A sharp click needs almost none. A soft or swelling attack needs more, or the front gets cut off. So you can adjust the number, and you adjust it per file, not per bank.

Drop a prepare.csv next to your samples:

# file, lead_ms, start_ms
kick.wav,    6,
snare.wav,    , 120
rim.wav,   0.5,

lead_ms adjusts the automatic guess. start_ms replaces the guess: the window begins exactly there. Use it when the part you want is not the first attack. Examples are the second hit of a flam, a tail alone, or a moment 300 ms into a sample. Files that you do not list use --lead-ms, which defaults to 3.

A filename in the CSV that is not in the folder is an error. A typo that does nothing, without a message, would be worse than an error.

Confirmed on a Digitone II. We flashed an image with marker samples at five known slots, and every marker played back from the TRAN parameter. That answers both open questions. These bytes are the FM drum transients. And the whole chain (locate, extract, replace, re-sign, flash) works from start to end.

Note: we measured the location, format, entry length and count of the bank. Elektron does not document them, so a future OS release could move them. When it runs, the mod finds the address through the boot stream. It refuses an image whose layout it does not recognise. It does not trust a stored constant.

LFO ONE and HALF: the right length, and a hold at the end

lfolength v1.0.1 Confirmed on hardware

The manual says TRIG MODE ONE runs the LFO for one cycle and stops, and HALF for half a cycle. The factory firmware gets both parts wrong, on audio and MIDI tracks. It stops at fixed points of the cycle, and does not count from the start phase. So with SPH moved, the LFO ends early: ONE from SPH 96 plays a quarter of a cycle, and HALF from SPH 64 plays a whole one. And at the stop, it jumps to the centre. So a square on the filter “turns off” in ONE and “jumps back to the middle” in HALF.

This mod fixes both. Source Source

Open the LFO ONE/HALF fix →

Runs entirely in your browser. There is no install and no command line, and nothing is uploaded.

Fixes
ONE and HALF end early (or HALF late) when SPH is not 0. ONE and HALF jump to the centre when they stop. On audio and MIDI tracks
Cause
The LFO code tests for the middle and the end of the cycle, not for half a cycle and a cycle since the trig. To stop, it writes a fixed value per waveform into the output. The fix counts from the start phase and removes those writes
Changes
8 edits in section 3 (4 hooks, 4 stores removed) and a 260 B code chunk the shared start-up loader copies to RAM
Tested
The emulator compared factory with fixed over every mode, waveform, start phase, speed direction, fade and retrig pattern. Only ONE and HALF change, and they trace the free-running waveform until they stop. Confirmed on a Digitone II on 2026-10-09, on an audio track (MIDI tracks: emulator only). ONE and HALF run their full length from every start phase tried (SPH 0 to 120), and hold. The hold was first confirmed on 2026-10-08 as LFO hold, which this supersedes. OS 1.12 has the same bugs

How mods stay compatible

The aim is that you can pick several mods and apply them together. That only works if each one can say, in advance, exactly which bytes it writes.

So every mod declares its extents (section, offset, length) before it changes anything. When you apply a set of mods, a check examines every pair for overlap. You can combine two mods that write disjoint bytes. The tool refuses two mods that collide, and names the exact range that overlaps.

In the browser, each tool page applies one mod. To combine mods, build on one page. Then load the downloaded file into the next page. Every mod checks that the bytes it will replace are still stock. So a page refuses an image where a different mod already wrote the same place. It does not write over it.

LFO Waves, Modulation Destinations and the MIDI Arpeggiator chain in any order, with the same result as the command line.

This is the weakest useful guarantee, on purpose. Disjoint bytes do not mean that two mods make sense together. They could write different regions and still fight over the same feature. A tool can check byte-range overlap, so the tool enforces it. We state this limit clearly.

Which pairs combine is the table at the top of this page, and each tool page shows its own mod's row of it.

Two rules every mod follows:

  • No section's unpacked content changes length. Resizing what lands in the instrument's memory would move every address after it, and nothing here can fix up the code that refers to them. The compressed size in the file can change. The section table records where each section sits, so no address points at it.
  • Integrity is not the task of a mod. Mods make section contents. The build path calculates the byte-sum, the content checksum and the HMAC signature again. Then it checks the result again. The tool never writes an image that fails the check.

The fix is on the command line (dnfw mods apply --mod songguard). A browser page, like the LFO Hold page, comes next.
Granular synthesis Planned After Waverider: grains read from tables or samples on the +Drive. It builds on the table store and reader of Waverider. We will estimate its cost per voice before we write it.
More LFO destinations Shipped twice 13 per-voice destinations were opened by a mask edit, and the 24 global FX destinations by a second mod that opens the enumeration as well. Master is what is left, and it needs destination codes above 127.
FX settings per pattern Costed Parameter locks are bound to a track by construction, so a pattern-wide FX lock needs storage the format does not have yet. Possible, but it means extending storage rather than flipping a flag.
